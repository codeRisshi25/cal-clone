# 🎯 Chapter 5: "Goated" Interview Preparation

An Interviewer won't just ask you "what" you built. They want to know "why" you built it that way, and "how" you'd make it better. Here is a cheat sheet to sound like a senior engineer during your analysis round.

---

## 🛠️ Typical "How would you add this feature" Questions

### 1. "How would you integrate Google Calendar?"
Right now, your app prevents double-bookings *inside* your app's database. But what if you have a dentist appointment on your actual Google Calendar?
**Your Strategy:**
- Add an OAuth 2.0 flow using `Passport.js` or standard Google APIs to let the Host log in with Google.
- Save their `google_access_token` and `google_refresh_token` securely in PostgreSQL.
- **The Magic Check:** When someone visits `/risshi/30-min-call`, instead of just checking the Prisma `Booking` database, your Express backend will also make a live HTTP GET request to the `Google Calendar API` asking for the Host's "Busy Slots" for that day.
- You merge the Google Busy Slots with your Prisma Booking Slots, and only show times that are free in *both*.

### 2. "How would you add Zoom or Google Meet links?"
**Your Strategy:**
- When the `POST /booking` route succeeds, don't just send an email immediately.
- Instead, make an HTTP POST request to the Zoom API (or Google Teams API) asking it to instantly generate a `meeting_url`.
- Save that `meeting_url` in the `Booking` database table.
- Inject that URL generated by Zoom right into the Resend Email confirmation template! 

### 3. "How would you handle Webhooks (e.g. telling Zapier when a meeting is booked)?"
**Your Strategy:**
- Create a `Webhook` table in Prisma with `url` and `userId`.
- When a booking is created, query the `Webhook` table for the Host. 
- Loop through the URLs and do a `fetch(webhook.url, { method: "POST", body: JSON.stringify(booking) })`.
- *Senior Tip:* "I wouldn't do this inside the main HTTP path because if the Zapier endpoint is slow, my user is stuck waiting. I would use a message queue like **RabbitMQ** or **BullMQ** (powered by our existing Redis server!) to handle dispatching the webhooks as a background job asynchronously."

## 🚦 Hard Technical Deep Dives

### "What exactly does your `entrypoint.sh` do in Docker?"
If they ask about deployment, explain the lifecycle:
1. Docker boots up.
2. `entrypoint.sh` executes first. It pauses for 15 seconds to ensure the PostgreSQL database (running in the same Azure container group) has time to wake up.
3. It runs `npx prisma db push`. This looks at our `schema.prisma` and forcibly synchronizes the Postgres Database to match our ideal structure.
4. It safely checks `node -e "..."` to see if there are 0 users in the Database. If so, it automatically injects (`seeds`) the admin user and test data.
5. Finally, it starts the live server via `exec node index.js`. 

### "Wait, you increased Azure Memory Limits? Why?"
**(This is a phenomenal story to tell! Ask them this!)**
"Originally we allocated `0.5 GB` of RAM to the Docker container in Azure. However, I found out the hard way that Prisma's heavy Rust Sync Engine combined with the Node.js V8 execution engine spiked memory usage rapidly over 500 MB during the `db push` schema synchronization. Azure caught this and instantly threw an Out-Of-Memory (OOM) `Platform Initiated Kill`. 

To fix this, I analyzed the deployment logs locally, bumped the Azure Container Instance (`deploy/aci-group.yaml`) to `1.5 GB` of RAM, and completely stabilized our CI/CD pipeline! That was a really fun DevOps debugging session."

## 🧠 Final Mindset Tips for the Interview
1. **Never say "I don't know".** Say: "I haven't implemented that specific layer yet, but if I did, I would approach it by..."
2. **Talk about Tradeoffs.** Don't just praise Redis. Point out that caching adds complexity to the system (Cache Invalidation architecture is notoriously difficult!). Point out that using Server Components in Next.js improves SEO, but makes the learning curve for React developers steeper.
3. **Be proud of the Automation.** Your project isn't just a basic web app. You actually built a full DevOps pipeline that catches schema errors on GitHub Actions *before* it spins up an isolated production cluster on Microsoft Azure. That's serious architecture!
